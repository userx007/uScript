12) MQTT plugin/driver
A. RECEIVE must be handled as MQTT.CMD < and MQTT.CMD < & when threaded
B.) all other commands must be integrated under MQTT.CMD > as parameters
From "PLUGIN.CMD > arg" perspective everything after > is a simple string argument (arg). The user shall avoid the pipe character '|' inside that string or border the string with brackets "").
An intermediary layer shall decompose that string provided as argument to the command  extract the MQTT specific command (SUBSCRIBE/UNSUBSCRIBE, PING, PUBLISH, etc.) and the arguments, validate them and then based on command type call the specific callback associated to that command with the arguments that follow after the command.

Actually the CMD is mapped directly to publish, the change shall make PUBLISH just another command under the other

Examples:

MQTT.CMD > SUBSCRIBE <topic> [qos] |
MQTT.CMD > UNSUBSCRIBE <topic>
MQTT.CMD > PING
MQTT.CMD > PUBLISH <topic>

The MQTT.CMD doesn't handle the xtra_args; if a command shall also receive something then use the standard syntax:

MQTT.CMD > send_side | receive_side

e.g.

MQTT.CMD > PUBLISH OPEN actuators/valve3/cmd | PUBACK

where:

PUBLISH - is the MQTT command extracted by the interḿediate layer which decides to callback to be used (here the publish_cb(..))
OPEN actuators/valve3/cmd - is the argument for the command
PUBACK is the message expected to be received (it has to be decoded to the exact real bytes to be received by that intermediary layer) and being on the receive_side of the CMD > fits natuaral in the implementation.
